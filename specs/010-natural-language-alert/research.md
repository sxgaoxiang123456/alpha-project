# Research: F8 自然语言设预警

**Feature**: specs/010-natural-language-alert  
**Date**: 2026-06-17

---

## 1. 自然语言解析引擎

### Decision
采用 **规则/正则优先 + LLM 兜底** 的混合解析方案。

### Rationale
- 核心句式（如「茅台跌破 1500 提醒我」）在 A 股盯盘场景下高度模式化，规则解析可以：
  - 在毫秒级完成解析，满足 p95 < 3 秒目标
  - 零额外 API 成本
  - 输出置信度可精确计算
- 复杂/同义表达（如「帮我盯着点茅台跌到一千五」）规则覆盖成本高，由 LLM 兜底：
  - F7 已落地 `BriefingLLMClient` 和 `PromptLoader`，可直接复用
  - 兜底调用量占比低，成本可控
- 混合方案兼顾响应速度、成本和覆盖率，避免纯 LLM 方案的不稳定性和高成本。

### Alternatives considered
- **纯规则/正则**：开发成本低，但同义词扩展困难，长尾句式覆盖不足，首次成功率难以达到 70%。
- **纯 LLM**：覆盖率高，但响应时间不可控（可能 > 3 秒），每次调用产生成本，且需要大量 Prompt 工程保证输出格式稳定。

## 2. 股票名称/代码匹配

### Decision
复用 MVP 的 `stock_search.py`，扩展候选排序与字段返回。

### Rationale
- MVP 已实现 A 股全市场代码表和名称模糊匹配，无需重复建设。
- 歧义场景需要候选列表，现有模块可扩展返回：
  - `stock_code`, `stock_name`, `sector`, `market_cap`
  - 按名称相似度 + 总市值排序
- 复用现有模块降低集成风险，保持数据一致性。

### Alternatives considered
- **新增独立股票索引服务**：引入 elasticsearch/milvus 等，成本高且与 MVP 架构不符。
- **前端匹配**：股票数据量大，前端匹配不适合；且后端已有数据源。

## 3. 规则创建与校验

### Decision
复用 MVP `alerts.py` router 和 `AlertRule` 模型创建规则。

### Rationale
- 自然语言解析完成后，得到的 `(stock_code, condition_type, threshold)` 与现有表单创建规则的数据结构一致。
- 复用已有规则校验逻辑（阈值有效、重复检测、上限检测）避免重复实现和状态不一致。
- 只需在自然语言 router 中调用现有 service 即可。

### Alternatives considered
- **独立 NL 规则创建路径**：重复实现校验逻辑，增加维护成本和 bug 风险。

## 4. LLM 选型

### Decision
使用 **GPT-4o-mini** 作为兜底模型，**DeepSeek-V3** 作为备选。

### Rationale
- GPT-4o-mini 在中文语义理解和结构化输出方面表现稳定，成本低。
- DeepSeek-V3 成本更低，可作为降备选或成本敏感时的切换方案。
- F7 已配置 `OPENAI_API_KEY` 和 `DEEPSEEK_API_KEY`，F8 直接复用同一套环境变量和客户端。
- 自然语言设预警调用频率远低于简报生成，预计月均成本 < 5 元。

### Alternatives considered
- **本地小模型（如 Qwen2.5-7B）**：需要额外部署资源，增加运维复杂度；MVP 阶段无 GPU 资源。
- **GPT-4o**：成本高于 GPT-4o-mini，解析任务不需要那么高的推理能力。

## 5. 候选列表排序

### Decision
按 **名称相似度优先，同分段按总市值降序**。

### Rationale
- 用户输入「银行」时，最直接的预期是找到名称最像「银行」的股票。
- 名称相似度相同时，大市值股票更可能是用户目标（如「招商银行」vs「江阴银行」）。
- 总市值数据可从现有 A 股代码表获取，无需额外数据源。

### Alternatives considered
- **总市值优先**：用户输入「银行」时，大市值银行股排前，但可能忽略名称相似度更高的中小银行。
- **成交量优先**：过于动态，不符合用户稳定找股票的预期。
- **自选股优先**：合理但增加耦合；若用户未加自选则退化为其他规则，优先保持简单。

## 6. 置信度计算

### Decision
采用 **多维度加权置信度**：股票识别 25% + 条件类型 25% + 阈值提取 25% + 整体语义一致性 25%。

### Rationale
- 每个维度独立可测试，便于调试和迭代。
- 规则解析器可精确判断每个维度是否命中。
- LLM 兜底时由模型输出整体置信度，后端映射到各维度加权。
- 阈值 0.7 为业务初始默认值，后续可根据首次成功率数据调整。

### Alternatives considered
- **单一 0/1 置信度**：过于粗糙，无法反映部分命中场景。
- **LLM logprob 平均**：规则解析阶段无 logprob 可用，不适合混合方案。

## 7. 输入入口设计

### Decision
在 Dashboard/自选股页/预警规则页分别新增 **独立的「一句话设预警」输入框**，不与现有搜索框复用。

### Rationale
- 复用搜索框会导致用户意图混淆：用户可能在搜索股票时意外触发预警创建。
- 独立输入框明确表达功能，降低认知负担，符合 F8「快速设置」的目标。
- 前端实现为独立组件 `nl_alert_input.html`，可复用于三个页面。

### Alternatives considered
- **复用搜索框**：通过「提醒我」等后缀区分，但容易误触发，增加错误创建风险。
- **仅在预警规则页提供入口**：覆盖不到 Dashboard/自选股页场景，降低入口可达性。
