## 1. 功能概述 *(mandatory)*

### 1.1 What

F8 自然语言设预警允许用户通过一句话创建价格/涨跌幅预警规则，无需手动填写表单。例如输入「茅台跌破 1500 提醒我」，系统自动解析出股票（贵州茅台，600519）、条件类型（价格低于）、阈值（1500），并在校验通过后创建预警规则。

### 1.2 Why

根据 PRD §3.1 主要画像，上班族散户希望快速设置监控规则，不想在表单中逐项选择股票、条件和阈值。自然语言设预警能显著降低创建规则的认知负担和操作步骤，验证「低密度信息 + 主动推送」模式下的交互效率。

### 1.3 MVP 约束

本功能属于 v1.1 阶段，需遵守以下约束：

- 仅服务**单用户**（延续 MVP 单用户架构）
- 仅覆盖 **A 股市场**
- 仅支持以下 4 种条件类型：
  - 价格高于（price_above）
  - 价格低于（price_below）
  - 涨跌幅高于（change_pct_above）
  - 涨跌幅低于（change_pct_below）
- 一次只处理**一只股票**和一个条件
- 不支持组合条件（如「茅台跌破 1500 且涨幅超过 5%」）
- 不支持历史时间范围、成交量、市值等复杂条件
- 不提供自然语言编辑/删除已有规则的功能
- 不提供多语言输入

## Clarifications

### Session 2026-06-17

- Q: 自然语言解析引擎采用什么方案？ → A: 混合方案（规则/正则做首次解析 + LLM 兜底/同义词扩展）
- Q: Dashboard/自选股页的入口是复用现有搜索框，还是新增独立输入框？ → A: 新增独立的一句话设预警输入框
- Q: 解析置信度如何计算？ → A: 多维度加权置信度（股票识别 25% + 条件类型 25% + 阈值提取 25% + 整体语义一致性 25%）
- Q: 股票名称歧义时，候选列表按什么排序？ → A: 名称相似度优先，同分段按总市值降序
- Q: 歧义候选确认后，用户如何“再次提交”？ → A: 前端自动携带原 query + 选中的 stock_code 重新请求，后端按指定股票创建规则

## 2. 运行环境 *(mandatory)*

### 2.1 入口

- **Dashboard 顶部「一句话设预警」输入框**：用户直接在 Dashboard 顶部新增的独立输入框中输入自然语言指令并确认，不占用原有股票搜索框
- **自选股页面「一句话设预警」输入框**：用户在自选股页面新增的独立输入框中输入自然语言指令并确认
- **预警规则页顶部「一句话设预警」输入框**：用户在预警规则页顶部的独立输入框中输入并确认

所有入口均为新增独立输入框，与现有搜索/筛选控件互不干扰。

### 2.2 输入

- `query`: string, 用户输入的自然语言，如「茅台跌破 1500 提醒我」
- 最大长度：200 个字符

### 2.3 输出

- `success`: bool, 是否成功创建规则
- `rule`: object, 创建成功的规则摘要 `{ stock_code, stock_name, condition_type, threshold }`
- `message`: string, 操作结果提示，如「预警已创建：贵州茅台 价格 < 1500」
- `candidates`: list[object] | None, 股票名称歧义时返回候选列表，每个候选至少包含 `{ stock_code, stock_name, sector, market_cap }`

## 3. 用户场景与验收 *(mandatory)*

### User Story 1 - 一句话创建价格预警（Priority: P1）

作为上班族散户，我想在搜索框输入「茅台跌破 1500 提醒我」，系统就能自动创建价格预警规则，省去逐项填写表单的麻烦。

**Why this priority**：这是 F8 的核心价值主张，直接降低创建预警规则的交互成本。

**Independent Test**：输入一个标准自然语言指令，3 秒内收到规则创建成功的确认。

**Acceptance Scenarios**：

1. **Given** 用户在搜索框输入「茅台跌破 1500 提醒我」，**When** 系统完成解析和创建，**Then** 返回 success=true，rule 包含 stock_code=600519、condition_type=price_below、threshold=1500，并提示「预警已创建：贵州茅台 价格 < 1500」
2. **Given** 用户输入「600519 涨到 1600 提醒我」，**When** 系统解析完成，**Then** 成功创建 price_above 条件，threshold=1600

---

### User Story 2 - 处理股票名称歧义（Priority: P1）

作为用户，当我输入的名称可能对应多只股票时（如「银行」），我希望系统给出候选列表让我选择，而不是随意创建错误规则。

**Why this priority**：避免误创建规则导致错误预警，保护用户信任。

**Independent Test**：输入歧义名称，系统返回候选列表而不是自动选择。

**Acceptance Scenarios**：

1. **Given** 用户输入「银行跌破 10 元提醒我」，**When** 系统解析到「银行」对应多只股票，**Then** 返回 success=false，candidates 包含至少 2 只银行类股票，message 提示「请从候选列表中选择具体股票」
2. **Given** 用户从候选列表中选择「招商银行」，**When** 前端自动携带原 query 与 stock_code=600036 再次提交，**Then** 成功创建规则

---

### User Story 3 - 拒绝低置信度解析（Priority: P2）

作为用户，当系统无法确定我的意图时，我希望它明确告诉我无法理解，并引导我使用表单创建，而不是猜测创建错误规则。

**Why this priority**：防止低质量规则污染预警系统，降低误报率。

**Independent Test**：输入模糊或无法解析的语句，系统拒绝创建并给出明确提示。

**Acceptance Scenarios**：

1. **Given** 用户输入「帮我看着点茅台」，**When** 系统解析置信度低于 0.7，**Then** 返回 success=false，message 提示「未能理解，请用『股票名+条件』格式重试，或前往预警页面手动配置」
2. **Given** 用户输入「茅台明天大涨」，**When** 系统无法识别具体条件阈值，**Then** 返回 success=false 并提示条件不明确

---

### User Story 4 - 不支持条件类型的提示（Priority: P2）

作为用户，当我输入了系统暂时不支持的条件（如成交量）时，我希望得到明确提示，而不是静默失败或创建错误规则。

**Why this priority**：管理用户预期，避免对未实现功能的困惑。

**Independent Test**：输入成交量相关指令，系统提示暂不支持。

**Acceptance Scenarios**：

1. **Given** 用户输入「茅台成交量突破 10 万手提醒我」，**When** 系统识别出条件类型为成交量，**Then** 返回 success=false，message 提示「暂不支持成交量条件，请使用价格或涨跌幅条件」

## 4. 边界条件与异常处理 *(mandatory)*

### 4.1 输入边界

- **空输入或纯空格**：返回「请输入预警条件」
- **超长输入（> 200 字符）**：返回「输入过长，请用一句话描述」
- **包含多个股票名**：如「茅台和五粮液都跌破 1500」，返回「一次仅支持一只股票」
- **包含多个条件**：如「茅台跌破 1500 或涨超 5%」，返回「暂不支持组合条件」
- **股票代码不存在**：返回「股票代码不存在，请检查输入」
- **阈值为非数字**：返回「未能识别阈值，请用数字表示价格或涨跌幅」

### 4.2 解析边界

- **解析置信度 < 0.7**：拒绝创建，提示用户重试或手动配置。置信度采用多维度加权：股票识别 25%、条件类型 25%、阈值提取 25%、整体语义一致性 25%
- **条件类型不支持**：明确提示支持的条件类型
- **股票名称歧义**：返回候选列表，不自动选择
- **股票名称完全无法匹配**：返回「未能找到匹配股票，请检查股票名称或代码」

### 4.3 业务边界

- **规则数量已达上限（50 条）**：返回「预警规则已达上限，请先删除其他规则」
- **相同规则已存在**：返回「该预警规则已存在，请勿重复创建」
- **股票不在自选股中**：仍可创建规则，但提示用户可将股票加入自选股
- **目标股票停牌**：允许创建规则，不做特殊处理

### 4.4 性能边界

- **解析响应时间**：p95 < 3 秒
- **候选列表长度**：最多 10 只股票；按名称相似度优先，同分段按总市值降序
- **并发请求**：单用户场景，无特殊并发要求

## 5. 业务流程 *(mandatory)*

```
用户输入自然语言 query
    │
    ▼
输入校验（长度、空值、多个股票/条件检测）
    │
    ├── 校验失败 ──→ 返回错误提示
    │
    ▼
解析 query
├── 提取股票名称/代码
├── 识别条件类型
└── 提取阈值
    │
    ├── 解析失败或置信度 < 0.7 ──→ 返回「未能理解」提示
    │
    ▼
股票匹配
├── 代码直接匹配 ──→ 唯一股票
├── 名称模糊匹配 ──→ 唯一股票
└── 名称歧义 ──→ 返回候选列表
    │
    ▼
规则校验
├── 条件类型是否支持？
├── 阈值是否有效？
├── 规则数量是否未达上限？
└── 是否重复？
    │
    ├── 校验失败 ──→ 返回具体错误
    │
    ▼
创建 AlertRule
    │
    ▼
返回成功确认
```

## 6. 需求 *(mandatory)*

### 6.1 Functional Requirements

- **FR-001**：系统 MUST 接受用户输入的自然语言 query 并尝试解析
- **FR-002**：系统 MUST 从 query 中提取目标股票名称或代码
- **FR-003**：系统 MUST 从 query 中识别条件类型（price_above / price_below / change_pct_above / change_pct_below）
- **FR-004**：系统 MUST 从 query 中提取数值阈值
- **FR-005**：系统 MUST 对模糊股票名称进行唯一匹配；歧义时返回候选列表，候选按名称相似度优先、同分段总市值降序排列，最多 10 只
- **FR-006**：系统 MUST 在解析置信度 < 0.7 时拒绝创建并提示用户
- **FR-007**：系统 MUST 对不支持的条件类型给出明确提示
- **FR-008**：系统 MUST 对空输入、超长输入、多股票、组合条件进行前端/后端校验
- **FR-009**：系统 MUST 对解析后的规则进行有效性校验（阈值有效、不重复、未达上限）
- **FR-010**：系统 MUST 在规则创建成功后返回确认信息，包含股票名、条件、阈值
- **FR-011**：系统 MUST 将创建成功的规则写入现有 AlertRule 模型
- **FR-012**：系统 MUST 在 Dashboard/自选股页/预警规则页提供独立的「一句话设预警」输入入口，不与现有搜索框复用
- **FR-013**：系统 MUST 在股票名称歧义时返回带 `stock_code` 的候选列表，并支持前端携带原 query 与选定 `stock_code` 再次提交以完成创建

### 6.2 Key Entities

- **NaturalLanguageQuery（自然语言查询）**：用户输入的原始文本、解析时间、解析状态
- **ParsedAlertIntent（解析后的预警意图）**：股票代码、股票名称、条件类型、阈值、置信度、歧义候选
- **StockCandidate（股票候选）**：代码、名称、所属行业、匹配分数
- **AlertRule（预警规则）**：复用 MVP 的 AlertRule 模型，包含 stock_code、condition_type、threshold、cooldown_minutes 等字段

## 7. 验收标准 *(mandatory)*

### 7.1 Measurable Outcomes

- **SC-001**：80% 的标准自然语言指令（股票名 + 价格/涨跌幅条件）能在 3 秒内成功创建规则
- **SC-002**：歧义名称返回候选列表的比例 > 95%
- **SC-003**：解析置信度 < 0.7 时拒绝创建的比例 > 99%
- **SC-004**：用户首次尝试成功创建规则的比例 > 70%
- **SC-005**：错误提示明确指向下一步操作（重试/选候选/手动配置）的比例 = 100%

### 7.2 Acceptance Criteria (Given/When/Then)

**AC-F8-01：标准价格预警创建**

- **Given** 用户输入「茅台跌破 1500 提醒我」
- **When** 系统完成解析
- **Then** 3 秒内返回 success=true，创建 rule { stock_code: "600519", condition_type: "price_below", threshold: 1500 }

**AC-F8-02：涨跌幅预警创建**

- **Given** 用户输入「五粮液跌幅超过 3% 提醒我」
- **When** 系统完成解析
- **Then** 成功创建 rule { condition_type: "change_pct_below", threshold: -3.0 }

**AC-F8-03：股票名称歧义处理**

- **Given** 用户输入「银行跌破 10 元提醒我」
- **When** 系统解析到多个候选
- **Then** 返回 candidates 列表，不自动创建规则

**AC-F8-04：低置信度拒绝**

- **Given** 用户输入「帮我看着点茅台」
- **When** 系统解析置信度低于 0.7
- **Then** 返回 success=false，提示用户重试或手动配置

**AC-F8-05：不支持条件类型提示**

- **Given** 用户输入「茅台成交量突破 10 万手提醒我」
- **When** 系统识别出成交量条件
- **Then** 返回 success=false，提示暂不支持成交量条件

**AC-F8-06：规则上限保护**

- **Given** 用户已创建 50 条预警规则
- **When** 用户通过自然语言尝试创建第 51 条
- **Then** 返回「预警规则已达上限」

## 8. 假设与依赖 *(mandatory)*

### 8.1 假设

- 用户输入以中文为主，允许包含 6 位股票代码
- 用户对 A 股基本术语熟悉（如「跌破」「涨超」「跌幅」）
- 单用户架构不变
- 股票基础信息（代码、名称、行业）可通过现有数据源查询
- **LLM 兜底能力由 F7 的 `BriefingLLMClient` 提供，API key 统一在 `backend/.env` 的 `DEEPSEEK_API_KEY` 中配置**
- 解析置信度阈值 0.7 为初始默认值，后续可根据反馈调整
- 置信度计算采用多维度加权：股票识别 25%、条件类型 25%、阈值提取 25%、整体语义一致性 25%

### 8.2 依赖

- 复用 MVP 的 `AlertRule` 模型创建规则
- 复用 MVP 的 `stock_search.py` 进行股票名称模糊匹配
- 复用 MVP 的 `alerts.py` router 已有规则创建能力
- 复用 MVP 的 `alerts` schema 进行规则校验
- 复用现有 A 股全市场代码表进行代码/名称匹配
- 复用 F7 已落地的 LLM 客户端作为自然语言解析兜底能力（v1.1 统一使用 DeepSeek-V4-Flash）
- 新增规则/正则解析器处理核心价格/涨跌幅句式

## 9. 功能边界 *(mandatory)*

### 9.1 In Scope

- 中文自然语言解析创建价格/涨跌幅预警
- 股票代码直接匹配
- 股票名称模糊匹配与歧义候选
- 解析置信度判断
- 条件类型：price_above / price_below / change_pct_above / change_pct_below
- 多入口支持（Dashboard/自选股页/预警规则页）
- 错误提示与引导

### 9.2 Out of Scope

- 多语言自然语言输入
- 语音输入
- 组合条件（AND/OR）
- 成交量、市值、PE 等复杂条件
- 自然语言编辑/删除已有规则
- 批量创建多只股票规则
- 智能推荐阈值
- 聊天记录上下文理解
